## 0. 한 줄 결론

코드는 실행되지만 **헤드라인 모델이 보고서가 설명하는 모델과 다릅니다.** 핵심 파생변수와 희귀범주 병합이 실제 모델에 들어가지 않았고, 변수 중요도 해석은 코드로 산출된 적이 없습니다. 데이터 누수는 "치명적"은 아니나 **CV 추정치를 낙관적으로 만드는 구조적 누수가 분명히 존재**합니다. 다만 데이터·서술·설계 의도가 모두 갖춰져 있어 **파이프라인만 바로 세우면 A급 포트폴리오가 되는 케이스**입니다.

## 3. 올바른 ML 파이프라인 (재설계)

```
원본 df_train (라벨 있음)
        │
        ▼
1. Train / Test Split  ← 가장 먼저 (private/test는 최종 보고 전까지 안 봄)
        │
        ▼
2. Feature Engineering  (total_sf, house_age → FunctionTransformer로 Pipeline 안에)
        │
        ▼
3. Preprocessing (ColumnTransformer)   ← 전부 Pipeline 내부 = fold마다 fit
   ├─ 수치형:  SimpleImputer(median) → StandardScaler
   ├─ 순서형:  OrdinalEncoder(명시적 categories)
   └─ 명목형:  SimpleImputer(most_frequent) → OneHotEncoder(handle_unknown='ignore', min_frequency=0.01)
        │
        ▼
4. Inner CV  → 하이퍼파라미터 튜닝 (GridSearchCV)
        │
        ▼
5. Outer CV(Nested) / held-out Test  → 비편향 일반화 성능 보고
        │
        ▼
6. Final Fit (전체 train) → coefficient 해석 → private 예측 → 제출
```

`min_frequency=0.01`이 **폴드별 train 기준**으로 rare를 자동 처리하므로 수동 병합(C3)이 불필요해집니다.

## 4. 재구현 실측 결과 (누수 제거 + 파생변수 포함)

5-Fold CV, 동일 데이터 기준:

| 모델 | 수정 후 CV RMSE | fold 표준편차 | 원본 보고값 |
|------|:---:|:---:|:---:|
| **ElasticNet** (α=0.01, l1=0.5) | **30,077** | **± 7,384** | 30,129.9 |
| Ridge (α=10) | 30,078 | ± 7,397 | 30,149.9 |
| Lasso (α=1.0) | 30,259 | ± 7,013 | 30,291.3 |

- **모델 간 평균 차이 ≈ 180 RMSE  vs  fold 표준편차 ≈ 7,300 RMSE** → 세 모델은 **통계적으로 동등**. "ElasticNet이 가장 견고"는 성립하지 않음(M2 확정).
- **누수 보정 전후 차이는 약 50 RMSE로 작음** → 누수는 *구조적으로* 존재했으나 *수치적* 영향은 작았음. (설계가 옳아서가 아니라 우연. 보고 가능한 형태로 바로잡음.)
- Held-out(20%) 단일 분할: **RMSE 22,446 / R² 0.907**. Nested CV: 약 30,000(±7,000)대.

### 실제 가격 결정 요인 (coefficient, $ 기준)

**▲ 상승:** Neighborhood(StoneBr +38,506 · NridgHt +31,183 · NoRidge +28,055), Bldg Type(1Fam +18,603), Gr Liv Area(+18,399/SD), Overall Qual(+14,080/SD)
**▼ 하락:** 일부 동네 더미(Gilbert −17,330, OldTown −10,118 등)

> **정정:** 실제 1순위 요인은 **입지(Neighborhood)와 건물 유형**이며, 기존 보고서의 "Total SF 최상위"는 해당 변수가 모델에 없던 버그의 산물입니다.

## 5. 수정된 결과 해석 (보고서에 그대로 쓸 문장)

1. **모델 선택:** "세 규제 모델의 CV RMSE 차이는 fold 표준편차(약 7,000)의 1% 미만으로 통계적으로 동등하다. 본 보고서는 성능 우위가 아니라, 단순성과 계수 안정성을 근거로 ElasticNet을 대표 모델로 채택한다."
2. **일반화 성능:** "선택과 측정을 분리한 Nested CV 기준 RMSE ≈ 30,000(±약 7,000)이며, 독립 held-out에서도 유사했다. 이는 그리드 최솟값을 보고하던 기존 방식의 낙관 편향을 제거한 값이다."
3. **가격 요인:** "계수 분석 결과 입지(Neighborhood)·건물 유형·지상 면적·전반 품질 순으로 가격을 끌어올렸다. '어디에 있는가'의 설명력이 '얼마나 큰가'보다 컸다."
4. **누수 통제:** "결측 대치·스케일링·인코딩을 전부 Pipeline 내부로 옮겨 각 폴드에서만 통계를 학습하도록 했다."

### 삭제하거나 다시 써야 할 기존 문장
- ❌ "ElasticNet이 가장 견고하여 최종 선정" → ✅ 동등성 하의 선택으로 수정
- ❌ "Total SF가 가장 중요한 가격 상승 요인" → ✅ 실제 계수 기반으로 재작성
- ❌ "rare 병합으로 차원폭발 방지" → ✅ "OneHotEncoder(min_frequency)로 폴드별 자동 처리"
- ❌ 부록 로그/스케일러/윈저라이징 비교 수치 → ✅ 재현 코드가 있는 것만 남기거나 "정성적 검토"로 표현 완화

## 6. 교수 예상 공격 포인트 (방어 준비)

1. "스케일러/임퓨터를 CV 전에 전체 train에 fit했죠? CV 누수 아닌가요?" → **기존 코드 방어 불가 / 수정본은 Pipeline 내부로 해결**
2. "`best_score_`는 그리드 최솟값인데 일반화 성능 근거는?" → **Nested CV로 대체**
3. "변수 중요도 표, 만든 코드 보여주세요." → **수정본 §6에서 실제 산출**
4. "`total_sf`가 최종 모델 컬럼에 있나요?" → 기존: 없음 / **수정본: 포함**
5. "모델 차이가 fold 표준편차보다 큰가요?" → **±7,300 제시로 동등성 인정**
6. (확인 필요) "평가가 log 스케일 R² 기준이면, 원본 타깃 학습을 정당화할 수 있나요?" → 부록 Cell 67 주석에 "평가 R²는 log 스케일"이라는 언급이 있어, **채점 기준이 log 스케일이면 log 타깃 변형도 별도 제출 권장.**
